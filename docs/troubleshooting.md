# Ошибки и восстановление работы

[← API и контроллер](api.md) · [README](../README.md) · [Разработка Макоры →](development.md)

Начните с состояния проекта: откройте доску и нужный этап. В Codex можно попросить навык `makora-control` проверить состояние. Повторная проверка читает существующую сессию и файлы; повторный запуск с замечаниями создаёт новую работу ИИ и расходует лимиты.

## Результат готов, но этап показывает ошибку

Если чат уже закончил работу, сначала используйте повторную проверку этапа. Не запускайте генерацию заново только для обновления статуса. Контроллер проверит сохранённый результат и его структуру.

Если ошибка остаётся, прочитайте её подробности: отсутствующий файл, неподходящий формат, непроверенный источник и незавершённый разговор требуют разных действий. Не заменяйте ошибку ручным статусом «готово»: следующий этап должен получить реальные документы.

## «Каждое ограничение должно быть точной цитатой исходного кейса»

Это сообщение проверки результата первого этапа, а не требование придумать ограничения. В `caseConstraints` допускаются только прямо заявленные ограничения исходного кейса. Если их нет, передаётся пустой список и блок ограничений не появляется.

Контроллер допускает различия пробелов и переносов строк, которые возникают при извлечении текста из PDF. Перефразирование, изменение чисел или знаков препинания точной цитатой не становятся. Для сканированного документа без текстового слоя сначала нужен OCR или текстовая версия.

Если результат был создан до исправления обработки пробелов, обновите Макору и повторно проверьте уже завершённый этап. Если ИИ действительно изменил цитату, отправьте замечание с просьбой исправить только результат. Не добавляйте отсутствующие в кейсе запреты ради прохождения проверки.

## Чат этапа не виден в проекте Codex

Проверьте, что открыт проект, который указан в `.makora/control.json`, и что сервер использует ту же папку. Репозиторий в подпапке `makora` и папка пользовательского проекта — разные пути.

Открытие результата или повторная проверка не должны каждый раз создавать новый чат. Новый запуск этапа должен создать отдельный чат Desktop с привязкой к проекту. Проверьте сообщение об ошибке создания чата и авторизацию Codex; не начинайте второй запуск вслепую, пока первый работает.

У фоновых агентов разработки другой способ исполнения. Если открыть их сессию в Desktop, приложение может показать, что она занята другим приложением. Это не означает, что обычный чат этапа подготовки должен работать так же. Не создавайте форк для изменения исполняемого агентом задания без понимания, куда попадёт его результат.

## Брейншторм ждёт, хотя документ уже написан

Черновик идеи ещё не является согласованным результатом. В чате сначала закончите сбор идеи словом «готово», затем посмотрите предложенные версии и экраны и отдельно подтвердите их. «Не готово» не считается завершением, а сообщение самого ИИ не заменяет подтверждение человека.

Дождитесь завершения ответа Codex и повторно проверьте этап. После публикации документов на доске утвердите результат. Подробный пример диалога — в [руководстве по брейншторму](brainstorm.md).

## Не получается перейти дальше после аналогов

У этапа аналогов есть два пути: уточнить результат и утвердить его либо продолжить без исправлений. Во втором случае непроверенные сведения сохраняют свой статус. Нельзя продолжить, пока сам поиск ещё выполняется. Переход ведёт к брейншторму, а не сразу к реализации.

PDF выгружается из разбора аналогов отдельным действием. Выгрузка не запускает новый поиск и не утверждает результат. Если файл не скачивается, проверьте ответ сервера и установленную зависимость ReportLab; JSON-команда контроллера не предназначена для скачивания бинарного PDF.

## Не проходят моки или схема экранов

- У каждой версии должны быть собственный начальный экран и полный список экранов. Переходы ссылаются на экраны этой же версии.
- Все пары «версия + экран» должны присутствовать в `mocks/screens.json`.
- Экран с данными ссылается на существующую фикстуру; статическому экрану без данных нужно объяснение.
- Сценарий использует существующие данные и локальную JSON Schema. Неверный сценарий должен содержать данные, которые нарушают корректную схему; отсутствующая схема не доказывает отрицательную проверку.

Сверьте имена и ID между документом версий, моками и сценарием. Исправлять нужно источник несоответствия, а не только видимую подпись на доске.

## Возвращённый ZIP не допускается к планированию

Загрузка архива только сохраняет и проверяет его. Для подготовки исходников используйте «Продолжить с этим сайтом». Проверьте сохранность исходных моков, допустимый состав архива и отчёт проверки окружения. Не добавляйте в ZIP `.git`, секреты и каталоги зависимостей.

Подготовка Git-проекта не означает, что приложение запущено или проверено человеком. Это следующие действия разработки. При изменённых исходных моках сначала разберитесь с расхождением, а не отключайте проверку.

## План не сохраняется или требует повторного утверждения

Проверьте уникальность ID, существование зависимостей и отсутствие циклов. Общий каркас должен быть началом графа; остальные задачи зависят от него напрямую или через другие задачи. Независимые задачи не должны владеть пересекающимися путями записи.

Лабораторная задача принадлежит одной лаборатории; задача подключения зависит от всех её задач и сама в лабораторию не входит. Корень мини-интерфейса имеет вид `labs/<id>/`.

Сохранённая правка плана переводит его на повторное рассмотрение. Если для проекта уже создан запуск разработки, изменение графа через прежний редактор блокируется: подготовьте новую ревизию планирования и утвердите её. Не подменяйте граф исполняемой очереди вручную.

## Не открывается лаборатория

Preview появляется для подходящей задачи с подготовленной рабочей копией и существующим скриптом. Команда состоит из `node`/`python`/`python3` и пути к скрипту внутри `uiRoot`; произвольная строка оболочки не допускается.

Скрипт должен учитывать `HOST` и `PORT`. Макора не устанавливает зависимости при нажатии preview. Проверьте лог в `laboratory-previews/` рабочей области сервера. Отсутствующий файл, ошибка запуска и отсутствие слушающего порта — разные причины отказа.

Принимается проверенный результат конкретной задачи. Если код изменился после приёмки, новый результат может потребовать повторных тестов, ревью и человеческого подтверждения. Подробности — в [руководстве по лабораториям](laboratories.md).

## Интеграция остановилась после успешных тестов

Успешные тесты относятся к определённому состоянию кода. Если основная ветка или рабочая копия изменились, контроллер должен обновить основание, повторить необходимые проверки и получить актуальное ревью. Старое подтверждение не является разрешением переносить произвольно изменённый код.

Для лаборатории дополнительно нужна человеческая приёмка текущего результата. Координатор может продолжать другие независимые задачи; если разрешённых действий больше нет, ожидание человека является нормальным состоянием.

## После обновления видна старая страница

Убедитесь, что обновлён именно репозиторий, из которого запущен сервер. Перезагрузите страницу с очисткой кеша. Если изменился Python-код, сервер нужно перезапустить; обновление файлов не заменяет уже загруженные модули процесса.

Не удаляйте `.makora` для исправления внешнего вида: там находятся документы, состояние и ссылки на чаты. При миграции процесса сохраняется резервная копия состояния; старые документы остаются историей, но не обязаны считаться утверждёнными результатами нового маршрута.

## Что сообщить при обращении за помощью

Укажите этап, действие перед ошибкой, её код и текст, версию репозитория и используемую папку проекта. Приложите обезличенный фрагмент результата или лога, который показывает проблему. Не публикуйте токены Codex, содержимое авторизации, личные документы или весь каталог `.makora`.
