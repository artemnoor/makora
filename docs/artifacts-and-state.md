# Документы, данные и состояние

[← Планирование и агенты](planning-and-agents.md) · [README](../README.md) · [Модели и навыки →](configuration.md)

Макора хранит не только последние Markdown-файлы. Отдельно существуют исходники кейса, документы этапов, сессии Codex, Git-запуски и результаты приёмки. Изменение одного из этих объектов не подменяет остальные.

## Папка проекта

```text
проект Codex/
├── AGENTS.md                         # Инструкция работать с этим проектом
├── makora/                           # Репозиторий приложения Макора
├── .agents/skills/                   # Установленные проектные навыки
├── input/
│   ├── brief.txt                     # Извлечённый текст кейса
│   ├── original/                     # Сохранённый исходный файл, если загружался
│   └── attachments/                  # Прикреплённые уточнения, если есть
├── artifacts/                       # Зарегистрированные документы и mocks/
├── reports/                         # Проверки этапов, настройки и агентные отчёты
├── exports/project-context.zip      # Пакет для внешнего агента
├── returns/                         # Сохранённые ZIP возвращённых проектов
└── .makora/
    ├── control.json                 # Корень проекта, репозиторий и порт
    ├── workspace/                   # Рабочие индексы локального сервера
    ├── preparation/
    │   ├── state.json               # Состояние подготовки
    │   ├── session-*/.../           # TASK, INPUT и result отдельных запросов
    │   ├── skill-snapshots/         # Снимки применённых навыков
    │   ├── projects/returned-*/     # Подготовленный код из возвращённого ZIP
    │   └── changes/                 # Предложения, diff и журнал применения правок
    └── agents/worktrees/            # Отдельные рабочие папки задач
```

Некоторые папки появляются только после соответствующих действий. В совместимых старых проектах расположение может отличаться.

### Где находится рабочий код

В маршруте с возвратом ZIP активная Git-папка берётся из `returnedProject.projectRoot`. Не нужно считать, что код всегда лежит в `app/`: эта папка используется как другое/резервное расположение, а подготовленный возвратный проект может находиться внутри `.makora/preparation/projects/`.

Чат подготовки открывается в корне проекта Codex. Рабочая папка задачи агента — отдельный worktree. Поэтому путь в чате и путь текущей реализации могут отличаться.

## Основные артефакты

| Этап | Файлы |
| --- | --- |
| Объяснение | `00_brief_explanation.md`; проверенные ограничения в состоянии и контексте |
| Аналоги | `02_competitors.md`, `02_competitors.json` |
| Брейншторм | `02_user_idea.md`, `02_versions_and_screens.md`, `02_versions_and_screens.json` |
| Моки | `mocks/fixtures/data.json`, `mocks/scenarios.json`, `mocks/screens.json`, схемы и `04_validation_report.md` |
| Пакет | `PROMPT.md`, `PREFLIGHT.json`, `ENVIRONMENT_CHECK.md`, `exports/project-context.zip` |
| План | `03_architecture.md`, `03_contracts/openapi.yaml`, `03_test_plan.md`, `03_tasks.json`, `03_execution.json` |
| Разработка | Git-коммиты, рабочие папки, тесты, ревью и записи запусков |

Числа в именах файлов исторические. Они не задают порядок этапов доски.

## Файлы одной сессии

**`TASK.json`** описывает этап: стабильный API-ID, `displayNumber`, вход, выход, обязательные файлы и пути к навыкам. **`INPUT.json`** содержит кейс, утверждённые материалы, предыдущие проверки, результаты и обратную связь. **`result.json`** содержит ответ для контроллера.

Пример формы результата пояснения, если в исходном кейсе действительно написано «Не более 10 записей»:

```json
{
  "files": {
    "00_brief_explanation.md": "## Что сделать\nКаталог событий.\n\n## Пример\nДопустим, человек ищет событие."
  },
  "constraints": [{"quote": "Не более 10 записей", "locator": "Раздел ограничения"}],
  "questions": [],
  "limitations": []
}
```

Основная форма `files` — объект «путь → содержимое». Для совместимости контроллер также принимает список объектов `path/content`, преобразуя его перед теми же проверками. Дубликаты путей и некорректные записи отклоняются. Это не разрешение записывать произвольный путь: проверки допустимых артефактов сохраняются.

`constraints` — цитаты исходного кейса для первого этапа. `limitations` в общих результатах — замечания к выполненной работе; их нельзя использовать, чтобы выдать придуманное ограничение за условие кейса.

## Как связаны моки и экраны

В `mocks/screens.json` хранится запись для каждой пары «версия/экран»:

```json
{
  "screens": [
    {"versionId": "v1", "screenId": "catalog", "fixtures": ["mocks/fixtures/data.json"]},
    {"versionId": "v1", "screenId": "about", "fixtures": [], "reason": "Статическая справка без данных"}
  ]
}
```

Это покрытие должно соответствовать согласованному документу версий. Для сценариев можно проверять отдельные части JSON через JSON Pointer, например `mocks/fixtures/data.json#/valid`.

Пример сценария:

```json
{
  "scenarios": [
    {"id": "valid", "fixture": "mocks/fixtures/data.json#/valid", "schema": "mocks/item.schema.json", "expectedValid": true},
    {"id": "invalid", "fixture": "mocks/fixtures/data.json#/invalid", "schema": "mocks/item.schema.json", "expectedValid": false}
  ]
}
```

`expectedValid:false` означает, что данные должны действительно нарушать корректную доступную схему. Отсутствие схемы не превращается в успешный негативный тест. Внешние схемы не загружаются автоматически по сети.

## Статусы этапа

| Статус | Значение | Обычное действие |
| --- | --- | --- |
| Нет записи | Этап не запускался | Завершить зависимости и начать |
| `launching` | Запрос подготавливается/отправляется | Дождаться подтверждения |
| `running` | Работа запущена | Следить за чатом и состоянием |
| `unconfirmed` | Доставка или результат не подтверждены | Проверить существующий чат, не дублировать запрос |
| `awaiting_idea` | Брейншторм ждёт человека или согласованного результата | Продолжить разговор в Codex |
| `failed` | Ошибка сессии или проверки файлов | Изучить причину, перепроверить либо исправить |
| `review` | Проверки пройдены; ждёт проверки человеком | Просмотреть документы и утвердить |
| `approved` | Этап утверждён | Перейти дальше |
| `continued` | Только аналоги: решили продолжить с текущими результатами | Сохранять пометки о непроверенном |
| `stale` | Результат требует обновления после изменений/миграции | Создать и согласовать актуальную редакцию |
| `stopping` / `cancelled` | Запрошена/подтверждена остановка | Дождаться терминального результата |

У сессии модели, импортируемого ZIP и задачи разработки другие наборы статусов. Например, `completed` у сессии не заменяет `approved` у этапа, а `prepared` у возвращённого проекта не является тестом приложения.

## Сохранение и повторная проверка

Контроллер сохраняет ID чата, запроса и операции. Перепроверка готового ответа читает сохранённый результат и повторяет проверки; она не должна создавать новый чат или заново отправлять задание ИИ.

Неопределённая доставка после сбоя не означает «точно не отправлено». Перед новым запуском нужно проверить, не существует ли уже нужный чат и результат.

## Изменения утверждённых материалов

Через `makora-change` или API создаётся предложение с точной базой, diff и анализом влияния. Подтверждённые зависимости и предполагаемые связи показываются отдельно. Применение требует подтверждения; если база изменилась, нужен новый анализ.

При частичной записи используется журнал восстановления. Конфликт не следует устранять ручной правкой состояния: так можно потерять связь между документами и проверками. После правки затронутые материалы требуют пересмотра и утверждения.

## Миграция старого процесса

Сохраняются прежние документы и чаты; создаётся `state-before-workflow-v3.json`. Старый анализ задания остаётся историей. Пояснение без нового учёта цитат, прежняя концепция и план могут получить `stale` и потребовать нового согласования.

Миграция не запускает ИИ повторно автоматически. Не удаляйте резервную копию и не переносите старые статусы `approved` в новые этапы вручную.
