# Разработка и проверка самой Макоры

[← Ошибки и восстановление](troubleshooting.md) · [README](../README.md) · [Архив →](history.md)

Эта страница предназначена для изменений приложения Макоры. Пользовательский проект, который создают агенты, имеет отдельную папку, план и очередь исполнения.

## Где находится реализация

| Область | Основные файлы | За что отвечают |
| --- | --- | --- |
| HTTP и локальная защита | `makora_core/server.py` | Маршруты, токен, проверка локальных запросов, выдача сайта |
| Текущий процесс | `makora_core/project_workflow.py` | Семь этапов, зависимости, согласования, переход к разработке |
| Общая подготовка | `makora_core/preparation.py` | Документы, сессии, импорт, ZIP и сохранение состояния; также совместимость прежнего процесса |
| Лаборатории | `makora_core/laboratories.py` | Проверка графа лабораторий и вычисление их состояния |
| Исполнение | `makora_core/agents/runtime.py` | Очередь, роли, рабочие копии, запуск агентов и preview |
| Приёмка | `makora_core/agents/acceptance.py` | Тесты, ревью, проверка актуальности кода и интеграция |
| Правки документов | `makora_core/artifact_changes.py` | Предложение изменений, влияние и применение |
| Проверка источников | `makora_core/source_verifier.py` | Проверки ссылок и подтверждающих фрагментов аналогов |
| Навыки | `skills/`, `makora_core/skill_manifest.py` | Методические инструкции и проверка состава снимка навыков |
| PDF аналогов | `makora_core/competitors_pdf.py` | Формирование отчёта; шрифты и лицензии хранятся вместе с реализацией |
| Контроллер проекта | `scripts/makora.py`, `setup.ps1` | Установка, запуск, состояние и запросы к API |
| Интерфейс | `dist/real-preparation.js`, `dist/agent-runtime-ui.js`, `dist/first-stage.js` | Доска этапов, разработка и оболочка страницы |
| Проверки | `tests/`, `.github/workflows/ci.yml` | Модульные проверки, браузерные сценарии и CI |

Не ориентируйтесь только на исторические имена файлов: `preparation` включает общий механизм, а новый порядок и его ограничения задаёт `ProjectWorkflow`. Аналогично `dist/` содержит рабочие исходники интерфейса, которые обслуживает сервер.

## Локальное окружение

Работайте из корня репозитория с Python 3.11+, Node.js 22.13+ и Git. Для установки в пользовательский проект применяется PowerShell 7 и `setup.ps1`; для изолированной разработки достаточно установить зависимости:

```powershell
python -m venv .venv
./.venv/Scripts/python.exe -m pip install -r requirements-dev.txt
npm ci
```

Не запускайте отладочный сервер поверх рабочего проекта. Пример отдельной среды на другом порте:

```powershell
./.venv/Scripts/python.exe -m makora_core.server --static dist --workspace C:\Temp\makora-docs-workspace --project-root C:\Temp\makora-docs-project --host 127.0.0.1 --port 8012
```

Папки примера должны быть отдельными тестовыми папками. Остановка отладочного процесса не должна останавливать пользовательский сервер на другом порте.

## Проверки перед публикацией

```powershell
./.venv/Scripts/python.exe scripts/check_skills.py
./.venv/Scripts/python.exe -m unittest discover -s tests -q
node tests/test_project_restore.mjs
```

Для браузерных проверок установите Chromium командой `npx playwright install chromium`. Набор `scripts/run_browser_checks.mjs` запускает текущие браузерные сценарии; окружение его сервера и параметры сверяйте с `.github/workflows/ci.yml` и самими сценариями. Они должны использовать выделенные тестовые данные.

CI запускает две группы: Python/навыки/восстановление проекта и браузерные сценарии. Стандартный набор включает подготовку, расположение этапов, один проект и маршрут workflow v3. Проверять нужно результат для опубликованного коммита, а не только прошлый зелёный запуск.

Модульные проверки полезны для схем, зависимостей, цитат, миграций и интеграционных ограничений. Браузерные сценарии с подменёнными HTTP-ответами проверяют интерфейс и взаимодействия, но не доказывают качество реального ответа модели.

## Реальные сессии Codex

Запуски реальных моделей расходуют лимиты авторизации. Они не нужны для каждой правки документации или подписи. Перед отдельным проверочным запуском прочитайте его сценарий: часть исторических E2E-скриптов рассчитана на прежний порядок этапов и конкретные тестовые порты.

Не используйте пользовательский кейс как фикстуру и не утверждайте его документы ради теста. Проверка генерации документов не доказывает, что прошли все циклы разработки, тестирования, ревью и интеграции. Успех отдельного preview тоже не равен готовности финального приложения.

## Как менять процесс

При изменении этапа проверьте его входы, схему результата, условия утверждения, зависимости следующего этапа и восстановление сохранённого состояния. UI и API используют стабильные ID; отображаемая позиция не заменяет ID запроса.

Изменение лабораторий затрагивает как минимум проверку плана, рабочие копии, preview, человеческую приёмку и интеграцию. Сохраняйте разделение функционального кода и `labs/<id>/`, а также привязку проверок к актуальному содержимому кода.

Правки навыка должны соответствовать формату результата, который принимает контроллер. После изменения навыка проверьте его структуру и учитывайте снимки уже созданных сессий: редактирование исходного `SKILL.md` не меняет их задним числом.

## Что не публиковать

В репозиторий не входят пользовательские `.makora/`, `output/`, окружения, личные исходные кейсы и секреты. В примерах документации используйте синтетические данные. Результаты старых прогонов находятся в [архиве](history.md) и описывают конкретные версии и границы проверки.
