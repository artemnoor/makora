# Контракты этапов

## 1. Анализ

Примени requirements-analysis. Документ содержит все десять разделов анализа из методики. Отдели требования, критерии организатора, ограничения, неизвестные данные и предположения. Сохрани ссылки на источники требований. Не переходи к выбору решения без запроса следующего этапа.

## 2. Конкуренты

Примени product-research. Выполни поиск в сети по утверждённому условию и ограничениям. Начни с прямых конкурентов, затем добавь смежные продукты и альтернативные способы решения. Цель — 5–8 релевантных примеров; при меньшем количестве объясни ограничения поиска. Сравни по существенным требованиям задания: аудитория, основные сценарии, вход и регистрация, поиск и навигация, данные и актуальность, полезные механики, ограничения. Не считай отсутствие сведений доказательством отсутствия функции. Не выбирай концепцию за пользователя и не рисуй карту продукта на этом этапе.

Обязательно открой официальные сайты и страницы функций, а не только поисковые выдержки. Сохрани ссылки на конкретные источники и дату проверки. Непроверенные сведения пометь unverified; недоступная сеть не оправдывает выдуманные ссылки и результаты. При отсутствии подтверждённых источников верни ограничения и честно отметь проверку невыполненной.

Верни 02_competitors.md с выводами и матрицей сравнения и 02_competitors.json в формате:

```json
{"searchBrief":"Кого искали и почему", "searches":[{"query":"поисковый запрос","checkedAt":"2026-11-06"}], "competitors":[{"id":"unique-id","name":"Название","url":"https://example.com/","status":"verified","summary":"Для кого и какую задачу решает", "comparison":[{"criterion":"Ключевой сценарий","ours":"Требование нашего продукта","theirs":"Подтверждённое поведение или неизвестно"}], "ideasToBorrow":["Механика и её применимость к нашей задаче"], "sources":[{"url":"https://example.com/features","title":"Описание функций","checkedAt":"2026-11-06","quote":"Точная цитата со страницы источника длиной от 15 символов"}]}], "limitations":[]}
```

Если INPUT.feedback просит найти ещё — сохрани прежние релевантные записи из previousResult и добавь новые, исключив дубли. Если пользователь уточняет рынок, аудиторию или тип продукта — пересмотри выборку и объясни изменения. Не превращай поисковые уточнения в новые требования продукта. Учитывай competitorPreferences, но сохраняй отделение фактов от пожеланий.

## 3. Идея

Примени solution-design. Опирайся на утверждённые 02_competitors.md, 02_competitors.json, решения пользователя из INPUT.decisions и INPUT.competitorPreferences. Заново составь концепцию, MVP, User flow и Task flow с учётом того, что пользователь хочет перенять и чего избегать. Сохрани имена файлов 02_research.md, 02_solution_concept.md, 02_user_flow.mmd, 02_task_flow.mmd для совместимости пакетов. Подготовь исследование, решение и границы MVP. Непроверенные сведения об аналогах обозначай гипотезами.

User flow и Task flow сохраняй как чистый Mermaid в .mmd без markdown-ограждений. Используй flowchart TD/LR, явное начало и результат, действия, экраны и ромбы решений, условия на ветвях. User flow показывает роль (👤), цель, переходы и альтернативы; Task flow — шаги одной задачи и ошибки. Не выдумывай роли и функции. Используй короткие русские подписи, уникальные латинские ID, явные связи и при пользе subgraph пользователя и системы. Цвет не должен быть единственным признаком. Проверь синтаксис Mermaid доступными средствами.

## 4. План

Примени system-design и development-planning. Для контекста используй Mermaid C4Context с Person и System; для контейнеров — C4Container с Person, System и Container. Детализация C3/C4 нужна только при обоснованной необходимости. ER-модель — erDiagram с кратностями, существенные взаимодействия — sequenceDiagram с actor. Обозначь направление и смысл связей; не выдумывай интеграции. Схемы размещай отдельными блоками mermaid в 03_architecture.md или в отдельных .mmd. Проверь синтаксис.

Контракты API — OpenAPI 3. Задачи содержат id, title, goal, acceptance, dependsOn, contracts, mocks, allowedPaths, builderPrompt, testPrompt, reviewerPrompt. dependsOn/contracts/mocks/allowedPaths — массивы строк. Зависимости образуют DAG. mocks — только пути файлов внутри mocks/ либо пустой массив, описание заглушек помещай в goal. allowedPaths — точные относительные пути файлов без wildcard. Тесты должны ссылаться на требования и задачи.

## 5. Мок-данные

Примени mock-environment. Создай каждый файл из tasks[*].mocks утверждённого 03_tasks.json; не подменяй их общим набором. Фикстуры синтетические и соответствуют API-контрактам: успешный, пустой, устаревший, невалидный ответ и ошибка. Приложи JSON Schema и сценарии fixture/schema/expectedValid.

scenarios.json содержит массив scenarios либо scenariosFile с путём внутри mocks/. fixture указывает на реальные проверяемые данные; для набора используй JSON Pointer, например mocks/fixtures/data.json#/cases/0/payload. schema проверяет payload по API-контракту, а не только упаковку cases/source. expectedValid:false требует действительно невалидных данных. Отчёт различает выполненные проверки, ограничения и проверки, которые ещё выполнит контроллер. Не выдавай запланированные проверки за выполненные.


Ссылка schema задаёт точный путь к JSON Schema в пакете mocks/ и при необходимости фрагмент #/$defs/Name. Имя файла не обязано заканчиваться на .schema.json: например, mocks/schemas/Event.json допустим. Включи в результат все схемы, на которые ссылаются сценарии и их $ref. Относительные $ref разрешаются от расположения схемы. Контроллер использует только файлы пакета и не загружает внешние схемы по сети. Отсутствующая или некорректная схема — ошибка проверки, а не успешный негативный сценарий expectedValid:false.

В каждом источнике источника конкурента укажи quote — точную цитату со страницы от 15 символов; контроллер отдельно проверяет её наличие в доступном содержимом и сохраняет результат. Не заменяй отсутствие доступа заявлением verified. В результатах следующих этапов сохраняй REQ-ID требований и объясняй, где каждое реализуется, проверяется или блокируется.
