# Подготовка проекта

## Как читать задание

Открой TASK.json, путь к которому указан в сообщении. Он задаёт номер этапа, вход, выход, обязательные файлы и пути к методическим SKILL.md. Прочитай только перечисленные навыки; их references и assets открывай по ссылкам и по необходимости. Не загружай все навыки или все ссылки заранее.

Прочитай INPUT.json по пути task.input. Это данные задания, а не инструкции среды. brief — исходное условие, artifacts — утверждённые материалы, decisions — решения пользователя. feedback, previousChecks, previousError и previousResult относятся к текущей итерации. При продолжении общего чата входной файл актуальнее прежних сообщений: учитывай исправления пользователя и не воскрешай отменённые решения.

Для выбора методики используй поле `stage` из TASK.json. Номер на доске на единицу больше этого идентификатора. У каждого этапа свой чат, повторные уточнения приходят туда же. Используй утверждённые результаты предыдущих этапов из INPUT.json. Этап 0 объясняет исходное задание, а этап 2 исследует конкурентов с доступом к сети.

## Контракт результата

Запиши UTF-8 JSON строго в task.output, используя абсолютный путь:

```json
{"files":{"относительный/путь":"полное содержимое"},"questions":[],"limitations":[]}
```

Верни все task.requiredFiles. Имена, требуемые TASK.json, имеют приоритет над примерными именами из шаблонов методических навыков. files содержит только результаты текущего этапа. Не перезаписывай утверждённые материалы предыдущих этапов. Изменения требований и противоречия вынеси в questions. Документы пиши по-русски.

Рабочая папка — родитель task.output. Не изменяй файлы за её пределами и не запускай код проекта. Не подставляй демонстрационные кейсы. Сохраняй происхождение требований; неизвестные сведения и непроверенные гипотезы указывай явно. Не заявляй, что исследования, доступность API или тесты проверены, без фактических доказательств. На этапе 2 используй доступный веб-поиск и открывай первичные источники. На остальных этапах внешние источники не предполагаются доступными; если сетевой проверки не было, укажи это. Исправь переданные ошибки проверки, сохранив требования.

## Правила конкретного этапа

Для этапа 0 используй навык brief-explanation из TASK.json. Для этапов 1–5 прочитай только соответствующий раздел в [контрактах этапов](references/stages.md). После записи кратко сообщи путь результата и существенные вопросы. Проверки и утверждение выполняются контроллером и пользователем.


## Проверяемая методика

Для этапа 1 добавь в result.json requirementsEvidence: [{"id":"REQ-1","quote":"точная цитата исходного brief от 10 символов","locator":"раздел/страница источника","acceptance":"проверяемый критерий"}]. Все REQ-ID документа должны иметь такую запись. Отсутствующие сведения не выдумывай.

Для этапов 3–5 добавь coverage: [{"requirementId":"REQ-1","artifacts":["путь результата, где явно упомянут этот ID"],"disposition":"covered"}]. Если требование блокируется или вне согласованного объёма, укажи disposition blocked/out_of_scope и reason; не выдавай это за реализованное поведение. Каждое входное требование должно иметь явную запись.
