# Макора в текущем проекте

Прочитай `.makora/control.json`: repository, projectRoot, port. Используй Python из `<repository>/.venv`, контроллер `<repository>/scripts/makora.py`, передавая `--project-root <projectRoot>` перед командой.

Сначала выполни `status`. Если сервер недоступен — `launch`, затем проверь `status`. При занятом порте другого проекта остановись с объяснением. Сайт открыт на http://127.0.0.1:<port> и использует то же состояние. Для GET: `request /api/preparation` или `request /api/agents/state`. Для POST запиши UTF-8 JSON в файл и выполни `request <route> --json <file>`. Токен контроллер получает сам; не печатай и не сохраняй его.

Свободные инструкции пользователя сопоставляй с текущими этапами и доступными навыками. Отвечай здесь, изучая input/, artifacts/, reports/ и app/. Не сбрасывай проект ради нового сообщения. Не редактируй файлы состояния `.makora` вручную.

При просьбе изменить существующую схему, User flow, документ, API или моки применяй навык makora-change. Он создаёт предложение и анализ влияния до перезаписи артефактов. Для уже изменённого пользователем файла передай его содержимое как предложение.

## Этапы и команды

Номер на доске на единицу больше идентификатора этапа в API.

- Простое объяснение (01 на доске): POST `/api/preparation/0/start`. Передай `{"brief":"полный текст задания"}` для нового проекта или `{}` для сохранённого задания. Применяется навык brief-explanation. Пояснение готово после проверок и доступно без утверждения.
- Анализ (02 на доске): POST `/api/preparation/1/start` с `{}` для сохранённого задания. Для следующих этапов подготовки используй идентификаторы 2–5 и проверь утверждение предыдущего этапа.
- Проверка результата: POST `/api/preparation/<stage>/refresh` с `{}`. Читай результат, ограничения и вопросы. Не отмечай отправленный запрос выполненной работой. При неопределённой доставке проверяй историю; не создавай дубликат.
- Аналоги (03 на доске, идентификатор 2): можно исправить разбор через feedback или перейти к своей идее с текущими результатами. POST `/api/preparation/idea/start` с `{"openInCodex":true}` создаёт отдельный чат этапа 04, где ИИ сначала выслушивает пользователя. Непроверенный разбор получает статус continued, его проверки сохраняются. Выбор по каждому аналогу необязателен.
- Идея (04 на доске, идентификатор 3): доска предлагает открыть созданный чат Codex и сформулировать задумку. Статус awaiting_idea означает ожидание обсуждения и документов. После согласования пользователь просит ИИ оформить результат по TASK.json; `/api/preparation/3/refresh` подхватывает result.json и запускает проверки. Повторный вызов `/api/preparation/idea/start` возвращает существующий чат.
- Открытие созданного чата: POST `/api/preparation/<stage>/open-codex` с `{}`. Поле desktopOpened подтверждает переход через Codex Desktop; desktopOpenError означает, что переход не подтверждён. Повторяй только открытие чата, не отправку задания. Ссылка codex:// сама по себе не доказывает, что приложение показало чат.
- Чаты этапов создаёт сам Desktop в проекте. Навыки перечислены в TASK.json и задании чата; для этого способа не заявляй нативные skill inputs. При открытии завершённого этапа старой версии API один раз создаёт discussionThreadId с сохранёнными материалами; исходный результат не перегенерируется.
- Утверждение: POST `/api/preparation/<stage>/approve` с `{}` после проверки результата и согласно поручению пользователя. Обязательные вопросы и ограничения не скрывай.
- Настройки моделей: GET `/api/preparation/agent-settings`, POST на тот же маршрут с актуальными projectId и roles. Сохраняй остальные роли. Используй каталог `/api/agents/status`.
- Прототип и разработка: POST `/api/preparation/development`, `{"stage":6}` или `{"stage":7}`.
- Махорага: GET `/api/agents/state`, POST `/api/agents/plans` с projectRoot (папка app/), brief (текст задания), context (утверждённые материалы). Для правок POST `/api/agents/plans/<id>/revise`, `{"feedback":"..."}`; утверждение `/api/agents/plans/<id>/approve`, `{}`. Используй возвращённый runId. Автопилот: `/api/agents/runs/<runId>/autopilot`, `{"enabled":true}` или false. Дополнительные маршруты и payload сверяй с `<repository>/makora_core/server.py` и `agents/runtime.py`.

Применяй установленные методические навыки: brief-explanation, requirements-analysis, product-research, solution-design, system-design, development-planning, mock-environment, prototype-handoff по задаче. Схемы сохраняй в Mermaid .mmd. Если пользователь просит работу напрямую в Codex, выполняй её с этими навыками; для регистрации результата в конвейере используй доступный API, не выдавай файлы вне конвейера за утверждённый этап. Изменения требований согласуй с уже утверждёнными документами; укажи, какие этапы требуют обновления.
