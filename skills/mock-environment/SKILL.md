# Мок-данные и заглушки

Вход: утверждённые контракты и модели, тест-план, User flow, задачи и допустимые источники данных. Прочитай [методику](references/methodology.md), [шаблон](assets/output-template.md), при необходимости [источники](references/sources.md).

1. Сопоставь компоненты и тесты с необходимыми сущностями, полями, состояниями и внешними зависимостями. Неподтверждённые контракты или отсутствующие данные отметь блокирующими там, где это действительно препятствует работе.
2. Создай синтетические фикстуры, соответствующие контракту, сохраняющие связи и воспроизводимые при документированном seed. Положительные и намеренно ошибочные данные храни отдельно, обозначив ожидаемое отклонение.
3. Составь применимые happy path, empty, invalid, unauthorized, not found, error и boundary сценарии. Для каждого укажи входы, данные, ожидаемый ответ и связанные ID тестов; не требуй сценарий, отсутствующий в контракте.
4. При необходимости подготовь заглушку на основе согласованного контракта существующим инструментом, например Prism. Если хватает файлов, отметь API как `skipped`; для состояния или сложной логики явно укажи ограничения и потребность в обработчиках.
5. Фактически проверь позитивные файлы по схемам, ожидаемое отклонение негативных, связи сценариев, доступность и контракт ответов запущенной заглушки. При недоступном инструменте или сервисе укажи `not_checked`; не называй моки проверкой реального продукта.
6. Запиши результаты из шаблона, включая команды, версии инструментов, время, полученные статусы и ошибки. Передай на согласование; изменения контракта требуют перепроверки зависимых данных.

Готовность: критичные потребности покрыты или отмечены блокерами, воспроизводимость и происхождение данных понятны, необходимые проверки действительно выполнены и результаты согласованы.
