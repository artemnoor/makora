# Архитектура и контракты

Вход: утверждённые требования, MVP, User flow, технологические ограничения и результаты исследования. Прочитай [методику](references/methodology.md), [шаблон выходов](assets/output-template.md), при необходимости [источники](references/sources.md).

1. Определи границы системы, пользователей, внешние зависимости и неизвестные интеграции. Подготовь C1 и C2 в Mermaid; компоненты C3 и код C4 добавляй при необходимости, указывая пропущенные уровни и причины.
2. Предложи логическую модель сущностей и ограничений, опираясь на функции MVP. ER и физическую базу используй, если они нужны задаче, а не по умолчанию.
3. Спроектируй контракты, необходимые для параллельной работы: операции, авторизация, запросы, ответы, ошибки, схемы и ссылки на требования. Для HTTP API используй OpenAPI 3.1.1, если инструменты проекта совместимы; иначе укажи согласованную версию и причину.
4. Зафиксируй альтернативы, выбранные технологии, компромиссы, незакрытые риски и решения, требующие подтверждения. Не навязывай стек, структуру репозитория или дополнительные сервисы.
5. Выполни доступную проверку контракта существующим валидатором и фиксируй фактический результат; если инструмент недоступен, отметь `not_checked`. Линтинг не подтверждает корректность реализации.
6. Создай применимые артефакты из шаблона; отсутствующий API или диаграмму отметь как неприменимые и объясни причину. Передай проект на согласование, не утверждай его за пользователя.

Готовность: архитектура и контракты покрывают MVP, границы и сомнения видны, тип и результат проверок указаны, решения готовы к экспертной оценке.
