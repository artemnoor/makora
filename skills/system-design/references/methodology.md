# Архитектурные решения

Создавай только те уровни C4, которые добавляют полезную детализацию. C1 показывает окружение; C2 — контейнеры и связи; C3 раскрывает выбранный контейнер; C4 описывает код, когда это оправданно. Логические сущности не доказывают наличие базы данных. Для внешних интеграций указывай доступность и собственника как неизвестные до реальной проверки.

Сохраняй ссылки `REQ → F → интерфейс/модель`. Для каждого существенного решения укажи альтернативы, причины, ограничения и последствия. Используй формат API, который соответствует выбранному взаимодействию; не создавай пустой OpenAPI для проекта без HTTP API. Проверяй совместимость OpenAPI с выбранным линтером и mock-инструментом.


## Схемы архитектуры

- Контекст C4: `C4Context`, `Person` / `Person_Ext`, `System` / `System_Ext`, `Rel`; люди, система и внешние зависимости имеют название, назначение и подписанные связи.
- Контейнеры C4: `C4Container`, граница `System_Boundary` или `Container_Boundary`, `Container` / `ContainerDb` и направленные отношения; компоненты рисуй только когда есть подтверждённые основания.
- Для структуры данных используй Mermaid `erDiagram` и корректные кратности; для обмена сообщениями — `sequenceDiagram` и `actor`, если в сценарии участвует человек. C3/C4 и sequence не обязательны без необходимости.
- Mermaid C4 является экспериментальной нотацией: используй поддерживаемые базовые конструкции, не рассчитывай на регистрацию внешних иконок. В Markdown отделяй каждую диаграмму блоком ```mermaid; отдельные `.mmd` содержат только код. Непроверенные зависимости явно помечай как неизвестные.
