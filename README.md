# Макора

Макора ведёт проект от условия хакатона до разработки через реальные сессии Codex GPT-6 Luna. Текущий пользовательский маршрут использует артефакты проекта вместо встроенного учебного кейса. При ошибке модели показывается ошибка; подстановки демонстрационных документов нет.

## Запуск

Python 3.11+, Node.js, PowerShell 7, Git и действующая авторизация Codex.

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
$env:CODEX_APP_SERVER_BINARY = "C:\CodexData\packages\app-server-daemon\releases\0.166.0-x86_64-pc-windows-msvc\bin\codex.exe"
.\.venv\Scripts\python.exe -m makora_core.server --static dist --workspace "$env:LOCALAPPDATA\Makora\workspace" --host 127.0.0.1 --port 8000
```

Открыть [localhost:8000](http://localhost:8000/). Путь к бинарнику нужно заменить при другой установленной версии Codex. Макора использует существующую авторизацию; секреты не нужно копировать в проект. На Windows порт занят эксклюзивно: второй сервер завершится ошибкой вместо обслуживания запросов старой версией.

Документы и история хранятся в указанной локальной папке. Для генерации текст задания и утверждённые материалы передаются реальной модели через Codex App Server. Запросы модели могут расходовать лимиты вашей подписки.

## Шесть этапов

1. **Анализ задания.** Ввод текста или извлечение текста PDF/DOCX/TXT/MD. Codex получает скилл `requirements-analysis` и формирует `01_case_analysis.md`. PDF без текстового слоя требует предварительного OCR.
2. **Разработка идеи.** Утверждённый анализ поступает в `product-research` и `solution-design`. Результат: исследование, концепция, User flow и Task flow. Сеть модели отключена: неподтверждённые сведения об аналогах остаются гипотезами и отражаются в ограничениях.
3. **Планирование.** `system-design` и `development-planning` создают архитектуру с Mermaid, OpenAPI, тест-план и задачи для агентов. Контроллер проверяет обязательные файлы, JSON, структуру OpenAPI 3, DAG и поля задач. Эти проверки не доказывают семантическую полноту архитектуры или полную корректность OpenAPI.
4. **Мок-данные.** `mock-environment` создаёт синтетические фикстуры, схемы и сценарии. Контроллер исполняет проверки JSON Schema, включая ожидаемо невалидные записи. Поддерживаются отдельные файлы и наборы с JSON Pointer, локальные ссылки между схемами; внешние схемы не загружаются. Запланированные тесты приложения не обозначаются выполненными.
5. **Рабочий прототип.** Макора создаёт отдельный Git-проект вне своего репозитория и сохраняет в нём утверждённые артефакты, исходные моки и решения пользователя. Существующий REAL-контроллер запускает Махорагу, Test Designer, Builder и Reviewer. Доступен экспорт реальных материалов и промпта для внешнего ИИ.
6. **Разработка агентами.** Открывается после интеграции всех задач и явного утверждения прототипа. Следующий план опирается на текущий Git-проект. Применяются реальные worktree, независимые sandbox-тесты, Reviewer, ограниченные циклы исправлений и подтверждаемая пользователем интеграция.

Этапы 1–4 требуют утверждения перед передачей результатов дальше. Ответы на вопросы и принятые допущения сохраняются в заметке утверждения. Повторная генерация снимает согласование последующих этапов и прототипа. Смена исходного задания создаёт новый идентификатор проекта; предыдущие данные сохраняются в локальной истории.

## Сессии и проверки

Генерация сохраняет thread ID, turn ID и operation ID. После перезапуска Макора проверяет конкретную сессию. При неопределённой доставке промпт автоматически повторно не отправляется. Завершённый ответ агента ещё не означает успешный этап: файлы проходят проверки и затем предлагаются человеку.

Статусы: выполняется, доставка не подтверждена, ошибка, готово к проверке, утверждено, требует обновления. Перепроверка файлов завершённого ответа выполняется без повторного запроса к модели. Содержание Markdown и Mermaid выводится на существующей доске; файлы JSON/YAML доступны для просмотра.

Код приложения выполняется только существующим sandbox-runner. Успешное текстовое заявление Reviewer не заменяет тесты. После переноса устаревшей параллельной ветки тесты и ревью выполняются заново. Неподтверждённые команды Codex показываются пользователю для разрешения; совпадения cwd недостаточно для автоматического одобрения.

## API подготовки

Все изменяющие запросы требуют same-origin управляющего токена, полученного через `/api/agents/token` с `X-Makora-Request: token`.

- `GET /api/preparation` — текущее состояние и сверка выполняющейся сессии.
- `POST /api/preparation/extract?name=brief.pdf` — извлечь текст файла.
- `POST /api/preparation/{1..4}/start` — выполнить этап, необязательный `feedback`; для первого — `brief`.
- `POST /api/preparation/{1..4}/refresh` — повторно проверить сессию и файлы.
- `POST /api/preparation/{1..4}/approve` — утвердить результат, необязательная заметка `note`.
- `GET /api/preparation/archive` — ZIP утверждённых документов, моков и промпта.
- `POST /api/preparation/development` — подготовить отдельный Git-проект, `stage: 5` или `6`.
- `POST /api/preparation/prototype/approve` — подтвердить прототип после фактической интеграции всех задач.

Реальная разработка использует прежние `/api/agents/*`. API итераций ZIP, ревизий и истории также сохранено. Исходные демонстрационные модули остаются в репозитории как прежняя реализация, но текущий входной маршрут их результаты не отображает.

## Проверки разработки

```powershell
python -m pip install -r requirements-dev.txt
python -m unittest discover -s tests -v
python scripts/check_skills.py
```

`tests/browser-preparation.js` проверяет текущий интерфейс с явно подменёнными HTTP-ответами. GitHub Actions запускает этот сценарий без обращения к модели. Старый `browser-flow.js` описывает прежний демонстрационный маршрут и не является проверкой текущего интерфейса.

`tests/browser-real-preparation.js` — отдельная платная по лимитам Codex проверка генерации этапов 1–4. Запускается только на выделенном E2E сервере порта 8780 с отдельной папкой `--workspace`. В ней допускается утверждение синтетического тестового кейса; пользовательские проекты она не обслуживает. Реальные end-to-end проверки разработки и их ограничения описаны в [отчёте](docs/real-codex-e2e-report.md). Успешная генерация документов не доказывает завершение всего агентного цикла.
