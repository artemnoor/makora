# Макора

Макора ведёт проект от условия хакатона до разработки через реальные сессии Codex с выбором модели и уровня рассуждений для каждой роли. Текущий пользовательский маршрут использует артефакты проекта вместо встроенного учебного кейса. При ошибке модели показывается ошибка; подстановки демонстрационных документов нет.

## Запуск

Рекомендуемый путь — установка из Codex Desktop, описанная ниже. Python 3.11+, Node.js 22+, PowerShell 7, Git и действующая авторизация Codex обязательны. Установщик запускает сайт локально и устанавливает зависимости. Секреты авторизации остаются в Codex, их не нужно копировать в проект. Запросы модели расходуют лимиты вашей подписки.

## Один проект Codex Desktop

Создайте и откройте папку проекта в Codex Desktop, затем отправьте в чат эту инструкцию:

> Склонируй [https://github.com/artemnoor/makora.git](https://github.com/artemnoor/makora.git) в подпапку makora. Прочитай AGENTS.md и установи Макору для текущей папки проекта через setup.ps1. После настройки запусти локальный сервер Макоры, проверь, что он работает, и дай ссылку на сайт. Затем используй навык makora-control.

Создайте папку проекта в Codex Desktop и попросите клонировать https://github.com/artemnoor/makora.git в подпапку `makora`. Из корня репозитория запустите:

```powershell
./setup.ps1 -ProjectRoot "C:\путь\к\проекту"
```

Установка создаёт локальное окружение, устанавливает зависимости и проектные навыки в `.agents/skills`, дополняет `AGENTS.md` и запускает сайт. На другом порте: `-Port 8001`. Требуются Python 3.11+, Node 22+, PowerShell 7, Git и авторизованный Codex. Навыки становятся доступны Codex при следующем чтении контекста проекта; при необходимости откройте новый чат в этом же проекте.

На сайте всегда открыт один проект: начните с загрузки условия. Выбора нового/существующего проекта и чата с Макорой на сайте нет. Документы, настройки и состояние сохраняются в выбранной папке. Старые папки проектов не удаляются. Переоткрытие сайта продолжает сохранённый этап.

В Codex попросите применить навык `makora-control`: он умеет читать общее состояние, запускать и утверждать этапы, менять настройки моделей и управлять Махорагой через тот же API, который использует сайт. Свободные задачи выполняются с методическими навыками; сгенерированный напрямую документ сам по себе не становится утверждённым результатом конвейера.

Контроллер: `python scripts/makora.py --project-root <папка> status`, `launch` или `request /api/agents/state`. Для POST используйте `request /api/... --json <файл.json>`. Он проверяет соответствие проекта серверу и получает локальный токен самостоятельно.

## Модели агентов

При создании проекта сначала создайте его папку, затем откройте «Модели и рассуждения агентов». Для Макоры (анализ и чат), Махораги, разработчиков, авторов тестов и ревьюеров можно выбрать разные модели и уровни рассуждений. Список берётся из текущего каталога Codex. «По умолчанию модели» оставляет выбор уровня за моделью.

Позже настройки доступны через кнопку «Настройки» в шапке и раздел «Настройки» на доске разработки. Настройка «Макора · этот проект» управляет моделью этапов подготовки в конвейере. Модель текущего чата Codex выбирается в самом Codex Desktop. На доске указана модель фактической сессии, а до запуска — настройка следующего запуска. Изменения сохраняются для выбранного проекта и применяются к новым сессиям; существующие сессии продолжают с прежними параметрами. Изменение настроек не меняет модель уже открытого чата Codex Desktop. Без настройки используется GPT-6 Luna с её уровнем рассуждений по умолчанию.

## Шесть этапов

1. **Анализ задания.** Ввод текста или извлечение текста PDF/DOCX/TXT/MD. Codex получает скилл `requirements-analysis` и формирует `01_case_analysis.md`. PDF без текстового слоя требует предварительного OCR.
2. **Анализ конкурентов.** Поиск прямых конкурентов и смежных альтернатив, сравнение по требованиям, ссылки на источники и даты проверки. Пользователь уточняет поиск и решает, какие механики перенять или исключить. Результат: 02_competitors.md и 02_competitors.json.
3. **Разработка идеи.** Утверждённые требования и сравнение конкурентов с комментарием пользователя поступают в solution-design. Создаются концепция, MVP, User flow и Task flow.
4. **Планирование.** system-design и development-planning создают архитектуру с Mermaid, OpenAPI, тест-план и задачи для агентов. Контроллер проверяет структуру артефактов и DAG задач.
5. **Мок-данные.** mock-environment создаёт фикстуры, JSON Schema и сценарии; контроллер проверяет данные по локальным ссылкам на схемы, включая негативные сценарии.
6. **Пакет для внешнего агента.** PROMPT.md и ZIP с утверждёнными материалами этапов 1–5, исходным условием, контрактами и моками. Возвращённый ZIP проекта сохраняется для продолжения работы.
7. **Разработка агентами.** Следующий план опирается на импортированный сайт или утверждённый прототип. Реальные worktree, независимые тесты, Reviewer и подтверждаемая пользователем интеграция.

Этапы 1–5 требуют утверждения. На этапе 2 обязателен комментарий о решениях по конкурентам. Повторный поиск или генерация делает последующие этапы и прототип устаревшими; документы сохраняются.

## Чаты этапов в Codex Desktop

Этапы: 1 — анализ задания; 2 — конкуренты; 3 — идея и схемы; 4 — план; 5 — мок-данные; 6 — пакет для внешнего агента; 7 — разработка. На втором этапе агент ищет конкурентов и альтернативы в сети, сравнивает их с требованиями и сохраняет источники с датами проверки. Пользователь может уточнять поиск, просить дополнительные варианты и комментировать полезные механики. Перед переходом к идее нужно сохранить решение о том, что перенять или чего избегать. Идея и схемы составляются по утверждённому сравнению и этому решению.

Этапы подготовки используют нативные входы `skill` в Codex App Server. Desktop app-tools не объявляются поддерживающими структурированные навыки. Перед отправкой мост подтверждает capability; несовместимая версия отклоняет запуск до отправки промпта. Для каждого запуска сохраняются копия всего пакета навыка, хеши файлов и версия пакета. Повторные задачи используют стабильную рабочую область сессии; каждая итерация сохраняется отдельно.

В Windows применяется явно обозначенный совместимый sandbox: запись ограничена рабочей областью, но полная изоляция чтения вне проекта не гарантируется. Это ограничение отображается в интерфейсе. Более строгая политика не включается скрытой подменой на полный доступ.


Модель и уровень рассуждений передаются из настроек Макоры при создании чата. Последующие этапы общего чата продолжают его с прежними параметрами. Чаты Desktop используют настройки доступа самого Desktop; ограничения изолированных рабочих сессий App Server к ним не применяются. В сообщении передаются только номер этапа и пути к навыку preparation-session и TASK.json. Контракт и методика читаются из файлов: TASK.json задаёт вход, результат, обязательные файлы и пути к нужным навыкам; INPUT.json содержит условие, утверждённые материалы и обратную связь. Полные тексты навыков в сообщения не вставляются. Агенты разработки продолжают использовать отдельные рабочие сессии и ограничения App Server.

## Сессии и проверки

Генерация сохраняет thread ID, turn ID и operation ID. После перезапуска Макора проверяет конкретную сессию. При неопределённой доставке промпт автоматически повторно не отправляется. Завершённый ответ агента ещё не означает успешный этап: файлы проходят проверки и затем предлагаются человеку.

Статусы: выполняется, доставка не подтверждена, ошибка, готово к проверке, утверждено, требует обновления. Перепроверка файлов завершённого ответа выполняется без повторного запроса к модели. Содержание Markdown и Mermaid выводится на существующей доске; файлы JSON/YAML доступны для просмотра.

Код приложения выполняется только существующим sandbox-runner. Успешное текстовое заявление Reviewer не заменяет тесты. После переноса устаревшей параллельной ветки тесты и ревью выполняются заново. Неподтверждённые команды Codex показываются пользователю для разрешения; совпадения cwd недостаточно для автоматического одобрения.

## API подготовки

Все изменяющие запросы требуют same-origin управляющего токена, полученного через `/api/agents/token` с `X-Makora-Request: token`.

- `GET /api/preparation` — текущее состояние и сверка выполняющейся сессии.
- `POST /api/preparation/chat/recover` — снять ожидание после ошибки или неподтверждённой доставки, сохранив историю. Сообщение не отправляется повторно; следующий вопрос создаёт отдельную сессию с историей разговора. Известный выполняющийся запрос эта операция не отсоединяет.
- `GET /api/agents/auth` — проверить авторизацию через `account/read` с обновлением токена; результат не содержит токены и данные аккаунта.
- `POST /api/agents/auth/login` — открыть видимую консоль PowerShell с `codex login` (Windows, требуется локальный токен страницы). Индикатор справа автоматически открывает восстановление при подтверждённой ошибке входа; при недоступном сервере вход не запускается. После входа нажмите «Проверить вход»; результат проверки кешируется до 30 секунд.
- `POST /api/preparation/extract?name=brief.pdf` — извлечь текст файла.
- `POST /api/preparation/{1..5}/start` — выполнить этап, необязательный `feedback`; для первого — `brief`.
- `POST /api/preparation/{1..4}/refresh` — повторно проверить сессию и файлы.
- `POST /api/preparation/{1..4}/approve` — утвердить результат, необязательная заметка `note`.
- `GET /api/preparation/archive` — ZIP утверждённых документов, моков и промпта.
- `POST /api/preparation/result?name=site.zip` — прикрепить готовый ZIP сайта (до 100 МБ); сохраняет архив и проверяет сохранность исходных моков без запуска кода.
- `GET /api/preparation/result` — скачать прикреплённый ZIP; результат загрузки сохраняется между перезапусками.
- `POST /api/preparation/result/continue` — подготовить загруженный сайт в отдельном Git-проекте для этапа 7. Исходные моки должны совпадать с утверждёнными; импорт не подтверждает работоспособность сайта. На доске после загрузки доступны «Продолжить с этим сайтом» и «Заменить ZIP».
- `POST /api/preparation/development` — подготовить отдельный Git-проект, `stage: 6` или `7`.
- `POST /api/preparation/prototype/approve` — подтвердить прототип после фактической интеграции всех задач.

Реальная разработка использует прежние `/api/agents/*`. API итераций ZIP, ревизий и истории также сохранено. Исходные демонстрационные модули остаются в репозитории как прежняя реализация, но текущий входной маршрут их результаты не отображает.

```powershell
python -m pip install -r requirements-dev.txt
python -m unittest discover -s tests -v

```

`tests/browser-preparation.js` проверяет текущий интерфейс с явно подменёнными HTTP-ответами. GitHub Actions запускает этот сценарий без обращения к модели. Старый `browser-flow.js` описывает прежний демонстрационный маршрут и не является проверкой текущего интерфейса.

`tests/browser-real-preparation.js` — отдельная платная по лимитам Codex проверка генерации этапов 1–5. Запускается только на выделенном E2E сервере порта 8780 с отдельной папкой `--workspace`. В ней допускается утверждение синтетического тестового кейса; пользовательские проекты она не обслуживает. Реальные end-to-end проверки разработки и их ограничения описаны в [отчёте](docs/real-codex-e2e-report.md). Успешная генерация документов не доказывает завершение всего агентного цикла.


## Изменение схемы или документа из чата

Навык `makora-change` обрабатывает просьбу изменить User flow, Mermaid-схему, требование, концепцию, API или моки. Контроллер сохраняет точную базу и diff, анализирует граф артефактов и различает подтверждённое влияние и предположения. Пользователь может передать уже изменённый файл: `scan` сравнит зарегистрированные файлы artifacts/ с сохранённой версией. Код внешних предложений не исполняется.

- GET `/api/preparation/changes/context` — файлы, владельцы этапов и baseDigest.
- POST `/api/preparation/changes` — request, targets, baseDigest, files с предлагаемым содержимым; без files — только анализ влияния.
- POST `/api/preparation/changes/scan` — request и targets для фактически изменённых файлов.
- GET `/api/preparation/changes` и `/changes/<id>` — список предложений и полный diff.
- POST `/api/preparation/changes/<id>/apply` — confirm:true и reviewStages после просмотра diff. Устаревшая база или неполный граф блокируют применение. Подтверждённые зависимости нельзя исключить из повторной проверки.
- GET `/api/preparation/changes/recovery` — состояние незавершённой транзакции. Ручное сохранение текущих файлов после конфликта требует confirm и expectedStateHash на `/changes/<id>/recovery`, затем нужен новый scan.

Применение журналируется до записи файлов. При перезапуске частичная запись откатывается либо завершается регистрация уже сохранённого состояния. Новые правки, появившиеся после аварии, не перезаписываются автоматически. Документы после правки требуют утверждения; экспорт блокируется до согласованного состояния всех этапов. История содержит основания пользовательского изменения.

## Проверки происхождения и реального выполнения

Анализ задания обязан предоставить requirementsEvidence с REQ-ID, точной цитатой brief, локатором и критерием. Последующие этапы дают coverage: артефакты с упоминанием REQ-ID либо явный blocker/исключение с причиной. Эти проверки подтверждают структуру и происхождение; они не доказывают полноту смысла требований.

Для конкурентов модель указывает цитату источника. Контроллер отдельно проверяет публичный URL, дату и совпадение цитаты, фиксирует хеш полученного содержимого. Проверка не выполняет JavaScript и не доказывает все функции продукта. Недоступная страница не помечается проверенной. По каждому конкуренту сохраняется решение borrow/adapt/avoid/research и комментарий; сохраняются изменения выборки.

`python scripts/smoke_native_skill.py` — opt-in реальный вызов Codex с навыком, который пишет изолированный проверочный файл. `--bridge` проверяет тот же маршрут через мост Макоры и её permission profile. Эти команды используют модель и её лимиты, поэтому не выполняются автоматически при каждом CI. Обычные тесты и fake HTTP browser journeys отдельно проверяют контракты и интерфейс.

Перед большой генерацией внешнему агенту передаётся ENVIRONMENT_CHECK.md и PREFLIGHT.json. Сначала он должен проверить чтение и создание ZIP. Возвращённый environment-proof.json проверяется по nonce; отсутствие файла означает not_checked, а не успешную проверку среды.
